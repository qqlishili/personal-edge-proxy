# 项目分析报告：yonggekkk/argosbx

- 项目地址：https://github.com/yonggekkk/argosbx
- 本地源码路径：`/root/code/argosbx`
- 分析基准：`personal-edge-proxy` 架构规范与 107.174.244.167 (1C2G) 运行环境

---

## 1. 项目架构与实现形态
- **技术栈**：Bash 自动化脚本 (`argosbx.sh`, 93KB) + Cloudflared (Argo Tunnel) + Sing-box / Xray 核心。
- **运行模式**：主打“无交互一键脚本”，核心机制是将本地代理入站通过 Cloudflare Argo 临时或固定隧道反向穿透到公网。
- **订阅分发机制**：与 `sing-box-yg` 一脉相承，使用 crontab `@reboot` 唤醒的 `busybox httpd` 提供静态订阅分发。

---

## 2. 核心优劣势对比（对比 personal-edge-proxy 需求）

### 优势
1. **死 IP 绝地求生能力**：当 VPS 物理 IP 被 GFW 完全墙阻断时，可通过 Cloudflare 隧道实现零公网入站穿透，复活可用性。
2. **极速一键部署**：参数化命令行执行，免去交互式问答流程。

### 劣势
1. **网络延迟与吞吐劣势明显**：Argo 隧道必须经过 Cloudflare 节点转发，带来额外的 150ms~300ms 网络延迟与频发的 TCP 重传，完全违背作为“链式代理快速落地节点”的低延迟诉求。
2. **当前 VPS 场景完全不适用**：本机 `107.174.244.167` 的 IP/端口完全健康且直连性能极佳，引入 Argo 隧道属于典型的“为伪需求引入重大性能降级”（逆向优化）。
3. **脆弱的进程与订阅守护**：同样采用野蛮的 busybox 临时后台进程，缺乏企业级 systemd 标准监控与自动恢复机制。
4. **与已存在脚本高度重复**：系作者由 `sing-box-yg` 剥离隧道特性的衍生版本，缺乏独立架构演进价值。

---

## 3. 适用性评级
- **当前机器适配度**：★☆☆☆☆ (2.0/10)
- **结论**：属于特定场景（IP 被墙后急救）的权宜补丁工具，作为日常健康机器的代理主架构在**性能与稳定性上均存在严重降级**。
