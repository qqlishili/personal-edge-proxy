# 项目分析报告：alireza0/s-ui

- 项目地址：https://github.com/alireza0/s-ui
- 本地源码路径：`/root/code/s-ui`
- 分析基准：`personal-edge-proxy` 架构规范与 107.174.244.167 (1C2G) 运行环境

---

## 1. 项目架构与实现形态
- **技术栈**：Go 语言单一编译二进制 + 嵌入式 Web 前端 (Vue) + 嵌入式 SQLite 数据库 + 嵌入式 sing-box 核心 (v1.14.1)。
- **运行模式**：单一 systemd 守护进程 (`s-ui.service`)，零外部语言解释器依赖（无需 Python/Node/Nginx/Caddy/PHP）。
- **网络监听设计**：
  - Web 管理面板与订阅分发服务端口独立隔离（可面板绑定 `127.0.0.1:2095`，仅开放订阅端口 `0.0.0.0:2096`）。
  - 原生支持 RESTful 多客户端格式动态订阅 (`/sub/:subid?format=clash` / `sing-box` / `base64`)。

---

## 2. 核心优劣势对比（对比 personal-edge-proxy 需求）

### 优势
1. **内存与资源开销极低**：单一进程总常驻内存仅约 9~15MB，对 2GB 内存物理机无任何 OOM 威胁。
2. **原生订阅分发闭环**：无需部署 edge-sub、subconverter 或 Nginx，单二进制原生完成 Clash/Mihomo 配置组装。
3. **架构正交与职责解耦**：入站协议配置（REALITY/SS-2022）、用户凭据与出站路由通过 SQLite 状态持久化，更新即时生效。
4. **运维与生命周期成本极低**：单一二进制文件，升级与回滚仅需替换单个文件并重启 systemd。
5. **安全攻击面极窄**：管理面板可完全绑定 loopback（仅通过 SSH 隧道/1Panel 反代访问），只向公网暴露协议入站与带 Token 的订阅端口。

### 劣势
1. **非纯文本声明式 GitOps**：节点与用户状态存储在 SQLite，批量自动化编排需通过 REST API，不如纯 JSON 配置直观。
2. **核心版本绑定**：sing-box 核心以内库形式编译进主二进制，无法独立热替换 sing-box 到最新未适配版本。
3. **上游社区活跃度波动**：属于海外开发者维护的独立分支，虽功能精简稳定，但对极小众新协议的跟进速度不如国内脚本群。
